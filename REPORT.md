# Technical Report: Student Performance & At-Risk Prediction

## 1. Executive summary
This project implements a decision-support prototype to identify students who may benefit from additional academic support. It predicts whether the next assessment score will be below 50 from historical learning signals. The model is advisory only and must not be used for automated punishment, grading or admission decisions.

## 2. Business problem and prediction design
- **Business decision supported:** whether an educator should review a student's learning context and consider offering support.
- **Prediction unit:** one student-term snapshot.
- **Prediction point:** after current-term attendance, assignment and prior assessment information is available, before the next assessment.
- **Target:** `at_risk = 1` if next assessment score < 50, else 0.
- **Horizon:** next assessment.

## 3. Dataset and feature choices
The project uses a reproducible synthetic dataset generated by `src/generate_data.py` with seed 42. It contains 2,600 rows (650 per term over four terms).

Features:
1. Attendance rate
2. Assignment completion
3. Previous average score
4. Score trend
5. Missed assignments
6. Study hours per week

The target score is used only to create the label. It is excluded from predictors. Student ID and term are also excluded. No protected or sensitive attributes are generated.

## 4. Data preparation and EDA
The training script reports dataset shape, missing values, duplicate count and target class distribution. The generator intentionally introduces a small amount of missing predictor data and a small number of out-of-range attendance values. Domain-range clipping is applied before modeling. Median imputation is part of each model pipeline and is fitted on training data only.

## 5. Leakage analysis and split strategy
The model uses only information available before the next assessment. `next_assessment_score` and `at_risk` are not model inputs. Student ID and term are excluded. A chronological split is used:
- Train: terms 1–2
- Validation: term 3
- Held-out test: term 4

The validation set selects the candidate model by F1. The test set is retained for final comparison.

## 6. Models
- **Baseline:** DummyClassifier using the most frequent training class.
- **Logistic Regression:** class-weighted logistic regression with median imputation and standard scaling.
- **Random Forest:** class-weighted random forest with 250 trees, depth limit and minimum leaf size.

## 8. Error analysis
For the selected Random Forest model, the held-out test confusion matrix (rows = actual, columns = predicted; class order 0 then 1) is `[[124, 77], [54, 395]]`. This means 124 true negatives, 77 false positives, 54 false negatives and 395 true positives. The confusion matrix is also saved in `reports/metrics.json`.

- **False positive:** a student is flagged although their next score is not below 50. This may prompt an unnecessary review or use support resources.
- **False negative:** a student is not flagged although their next score is below 50. This may delay support for a student who could benefit from it.

In this education-support setting, false negatives deserve particular attention, while false positives should be managed through a supportive, low-cost human check-in rather than punitive action.

## 9. Explainability
The app displays simple, understandable signals based on the submitted inputs, such as low attendance, low assignment completion, low previous average, declining score trend, missed assignments and low study time. The training script also calculates permutation importance on validation data and saves it to `reports/feature_importance.csv`.

These signals are not causal explanations. They are prompts for a teacher to investigate context.

## 10. Limitations, bias, privacy and responsible use
The dataset is synthetic, so the metrics do not prove real-world performance. The generator encodes simplified relationships and cannot represent every school, subject, student or assessment type. Data quality, missing context and changes in teaching or assessment can affect predictions. No real personal student data is used.

A real deployment would require consent and governance, privacy and security controls, representative data, fairness evaluation, probability calibration, monitoring and educator/student feedback. The output must remain advisory and subject to human review.
